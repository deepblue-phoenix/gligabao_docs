`internal/api/training/datasets.go`, `internal/db/relational/model/training_dataset.go`, `sidecar/ai_train/api/models.py`, `sidecar/ai_train/ai_train_core/dataset.py`, `sidecar/ai_train/ai_train_core/prompt_format.py`, `sidecar/ai_train/finetune_data/`

A training dataset is a `.jsonl` file. **Datasets are managed by the Go server alone**: it keeps the files and their records and it serves the REST endpoints that external clients and the admin UI use. The sidecar and the Modal app have no dataset endpoints; they only store a dataset internally, on the data volume (`/data`), when a job needs it. A training dataset is separate from a memory [dataset](/concepts/datasets), which is a container of artifacts, entities and edges in the database.

## Format

Each line is one training example:

| Key | Meaning |
| --- | --- |
| `instruction` | The task or user query, e.g. "Find news about NVIDIA and buy 10 shares". |
| `input` | Extra context. Often an empty string. |
| `output` | The expected multi-step answer, including tool usage. |

```json
{"instruction": "Check recent news about NVIDIA and buy 10 shares if it's positive", "input": "", "output": "I'll research NVIDIA news... [tool calls and reasoning]"}
```

Training turns each line into a string with Gemma 4's turn markers (`format_instruction` in `ai_train_core/prompt_format.py`; inference uses the same format):

```
<|turn>user
{instruction}

{input}<turn|>
<|turn>model
{output}<turn|>
```

Without an `input` the blank line and `{input}` are left out.

- **`<|turn>` and `<turn|>`** are single special tokens of Gemma 4 (ids 105 and 106). `<turn|>` ends a turn and is the token generation stops on (the base model's `generation_config.eos_token_id` is `[1, 106, 50]`). The dataset file has no EOS and should not: `format_instruction` puts `<turn|>` at the end of every example, and the tests check against the real Gemma 4 tokenizer that the encoded text ends with id 106. `SFTTrainer` also appends the tokenizer's `eos_token` (`<eos>`) when the text does not end with it; both stop generation.
- **Not `<start_of_turn>` / `<end_of_turn>`:** those are Gemma 2/3's markers and are not in Gemma 4's vocabulary, so they are tokenized as plain text. A model trained on them learns to spell `<end_of_turn>` instead of emitting the stop token and its replies run to `max_tokens`, inventing further turns. gligabao used them up to 0.46.0; **adapters trained with that version must be retrained.**
- **`<bos>`:** Gemma 4's chat template starts with it, but the tokenizer does not necessarily add it. `bos_prefix(tokenizer)` prepends it to the training text and to the inference prompt only when the tokenizer does not, so both have exactly one.

`load_training_dataset()` (`training_common.py`) reads the file, maps each entry through the formatter into a `text` field, and builds a Hugging Face `Dataset`; `run_finetuning` adds the `<bos>` prefix and hands it to the `SFTTrainer` with `formatting_func` returning that `text`.

The bundled dataset (`finetune_data/`, 325 tool-calling examples on news and finance) is generated by `finetune_data/generate_dataset.py`. `modal run app.py --action validate` checks the remote dataset.

## Managing datasets (Go server)

The Go server validates, stores and lists datasets; the sidecar is not involved.

| Endpoint | Behaviour |
| --- | --- |
| `POST /v1/gb/training/datasets[?db=]` | Uploads a dataset: a multipart form with the file in the field `file` (and optionally `filename`, which overrides the file's name). The server validates it (UTF-8, every non-blank line a JSON object with string `instruction` and `output` and, if present, a string `input`; a plain `*.jsonl` name; at most 64 MB), saves it in the training dataset directory and records it in `gb_training_datasets`. Uploading a name again replaces the dataset. `201` with the record, `400` for an invalid file, `413` if too large. |
| `GET /v1/gb/training/datasets[?db=]` | `{"datasets": [...]}`, the records, latest upload first. It is read from the database only, so it works with the sidecar or Modal down. |

The files live in the training dataset directory, `<db path without extension>.training_datasets` next to the database by default (e.g. `bin/gligabao.training_datasets`); override it with `serve --training-dataset-dir <path>` or `ServeOptions.TrainingDatasetDir` when embedding. The upload saves the file first as a temporary file, records it, then renames it into place, so a failure leaves neither a record without its file nor a half-written file.

### The `gb_training_datasets` record

One row per file name (Go: `relational.TrainingDataset`):

| Field | Meaning |
| --- | --- |
| `id` | The record. |
| `filename` | A plain `*.jsonl` name, unique. It names the file in the directory and the dataset on the sidecar. |
| `size_bytes`, `num_records`, `sha256` | Size, number of non-blank lines, and hex SHA-256 of the file. |
| `status` | `stored` (only on the Go server) or `synced` (a job has taken this version of the file to the sidecar). Uploading the name again makes it `stored` again. |
| `created_at`, `updated_at` | When the record was made; when the file was last uploaded. |
| `synced_at` | When the sidecar last took the current file; null while it has not. |

## How a dataset reaches the sidecar

Only through a job start. When `POST /v1/gb/training/jobs` names a `dataset`, the Go server finds its record (an unknown name is a `400`), reads the file from the directory, checks it against the record's `sha256` (a missing or changed file is a `500` that asks for a new upload) and sends it to the sidecar in the `POST /training/job_start` request, as `dataset_content` (base64) next to `dataset`. The Go client has no other dataset call. Once the sidecar has taken the job the record becomes `synced`. The file is sent with every job that uses the dataset, so a sidecar whose volume lost the file still works. A client of the Go server cannot send `dataset_content` itself.

The sidecar (the Modal web API) stores `dataset_content` on the data volume as `/data/<dataset>`, replacing an earlier file of that name, and commits the volume before it spawns the job (`store_dataset` in `ai_train_core/dataset.py`). `400` if `dataset` is not a plain `*.jsonl` name (no path, no leading dot), if `dataset_content` is not valid base64 or is empty, or if there is a `dataset_content` without a `dataset`. Without `dataset_content`, `dataset` must already be on the volume (also `400`).

## `TrainingDataset` (Python)

`TrainingDataset` (pydantic, `sidecar/ai_train/api/models.py`) is how the sidecar loads and passes a dataset around internally; it is not an endpoint body:

| Field | Meaning |
| --- | --- |
| `filename` | The file name. Required. |
| `content` | Base64 of the jsonl file. It is **never serialized**. |
| `size_bytes` | Size of the file. |
| `uploaded_at` | When it was stored. |
| `modified_at` | The file's modification time. |

`payload()` returns the decoded bytes and raises `ValueError` if `content` is missing, empty or not base64. `TrainingDataset.from_path(path, with_content=False)` loads a file (with its content only if asked). Timestamps are timezone-aware UTC.

## Choosing the dataset of a job

A job names its dataset by file name, in the `dataset` field of `POST /v1/gb/training/jobs`: one of the uploaded datasets (the **training** view of the admin UI fills its picker from `GET /v1/gb/training/datasets`). Without a `dataset` the job trains on the sidecar's default dataset, `/data/gemma4_tool_calling_news_finance_v1.jsonl` (what `modal run app.py --action sync` writes).

`modal run app.py --action sync` is the CLI way to write the default dataset: it uploads the local `finetune_data` file, but only if it is newer than the remote one. `--action train` does it first.
