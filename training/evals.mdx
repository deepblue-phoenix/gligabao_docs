`evals/training/` (`dataset.go`, `eval.go`, `judge.go`), `internal/api/training/evals.go`, `internal/db/relational/model/trained_model_eval.go`, `internal/db/relational/{sqlite,postgres}/db_trained_model_eval.go`, `admin_ui/src/training.ts`

An **eval** of a trained model asks the model the questions of a dataset and has an external LLM judge how closely its answers agree with the dataset's. For now the dataset is the model's own **training dataset**, so the score says how well the model learned what it was trained on. The code is the eval subsystem [`evals/training`](https://github.com/deepblue-phoenix/gligabao/blob/main/evals/training/README.md) (the logic) and `internal/api/training/evals.go` (the HTTP endpoints and the background runner). It is separate from the knowledge-extraction evals ([Evals](/operations/evals), `evals/knowledge`).

## What happens

`POST /v1/gb/training/models/{id}/evals` (the **Eval** button in the admin UI):

1. The server finds the model's dataset by the name recorded when it was trained (`dataset`, without `.jsonl`) in the training datasets directory ([Training datasets](/training/datasets)). It must still be there: a model trained on the sidecar's default dataset (jobs from before datasets were required) or a dataset that was deleted answers `400`. The sha256 of the file read is stored with the eval; if it differs from the model's `dataset_sha256`, the UI shows "dataset changed since training".
2. A row of `gb_trained_model_evals` is made (status `running`) and the request answers `202` with it. The eval goes on in the background.
3. The examples are processed in **batches** of `batch_size` (default 10). For each batch the model answers every question (one sidecar `POST /infer/query` per question, with the training prompt: the `instruction`, and the `input` after a blank line; `max_tokens` 1024 and `temperature` 0.1 unless set), then the batch is judged by **one** LLM call. The judge LLM is the one the server uses for knowledge ingestion (the Anthropic client; `judge_model` picks another of its models). Its calls are recorded in `gb_inferences` (type `eval_judge`, stage `judge`) like the other LLM calls, and totalled on the eval.
4. After each batch its items are stored in `gb_trained_model_eval_items` and the counters of the eval row are updated, so the progress can be read at any time. The eval ends `completed`, `cancelled` (by the user; what was done is kept) or `failed` (with an `error`: the model or the judge kept failing, see the [How the judge works](#how-the-judge-works)). Evals that were running when the server stopped are marked `failed` at the next start.

Only one eval per trained model runs at a time (`409` otherwise). Inference requests of an eval are not stored in the model's request history (`gb_trained_model_inferences`), they are the eval's items.

The trained model is asked **one question per prompt, one question at a time**, in dataset order; only the judge works in batches (see [Why one question per prompt](#why-one-question-per-prompt)). A cold model makes the first question slow (the model load, see [Cold and warm starts](/training/modal#cold-and-warm-starts)); the rest run warm. A full eval of a 500-example dataset is 500 inferences, so it takes a while: use `limit` to try it on the first few.

## Why one question per prompt

The trained model is asked **exactly one question per prompt**, never several questions in one prompt. Only the judge works in batches. This matters for the Gemma 4 models gligabao fine-tunes (E4B, the "4b", and the 12b), and the eval is built around it:

- **The model was trained on single turns.** Every training example is one user turn with one question and one model turn with its answer (`<|turn>user\nQ<turn|>\n<|turn>model\nA<turn|>`, see [Training datasets](/training/datasets#format)). A prompt that holds ten questions is a shape the model never saw. It may answer only the first one, run the answers together, drop the short answer style it learned, or invent a list format. An eval like that would measure how well the model follows a multi-question instruction, not what it learned from the dataset, and it would score a model lower for a reason that has nothing to do with its training.
- **Small models interfere across items.** At 4B and 12B parameters the questions in one context bleed into each other: a fact asked about in question 2 shows up in the answer to question 5, and the answers get worse as the prompt grows. Which questions are answered well would then depend on what they were batched with, so the same question could score differently from one eval to the next.
- **The output budget is shared.** One `max_tokens` would cover all the answers, so the last ones are cut off first, and the answers have to be split back out by position, which is one more place to go wrong (a missing or merged answer shifts all the later ones onto the wrong questions).
- **The check is on the training prompt.** The eval asks whether the model reproduces its training answers for the prompt shape it was trained on, one question and one answer. Only the single-question prompt tests that.

So the model is asked sequentially (one sidecar `POST /infer/query` per question, in dataset order), and the answers are kept per question.

**Two things that are not the same as putting several questions in one prompt:**

- *Batching at the inference engine*: running several independent prompts as separate sequences in one GPU `generate` call (left-padded, with attention masks). Each sequence still sees only its own question, so the answers match the one-at-a-time ones up to small numerical differences, and it would be much faster. gligabao does not do it: the sidecar's `/infer/query` takes one prompt per call. If it is added, compare its answers with the single-prompt ones before trusting its scores.
- *Parallel calls*: several `/infer/query` calls at once are correct too, but a Modal inference function that gets parallel calls starts more GPU containers, each of which loads the model, so the eval does not offer it.

**The judge is different.** It is a large LLM that grades *independent* items (a JSON array of question, reference and answer, with an id each), not a small model being asked to answer from its own weights, so batching them (10 by default, at most 25) costs one call per batch and does not change what is measured. Batching can still have small effects on the judge's scores: it may drift or anchor on earlier items in the batch. To check it, run the same eval on a sample (`limit`) with `batch_size` 1 and with 10 and compare the mean scores; if they differ noticeably, use a smaller batch.

## The score

The judge gives each answer 0 to 5 against the dataset's answer: 5 same, 4 correct with minor differences, 3 partly correct, 2 mostly wrong, 1 wrong, 0 empty/nonsense/refusal. 4 or 5 is **correct**, 2 or 3 **partial**, 0 or 1 **incorrect**. An eval reports the mean score of the judged items (0 to 5), the share of correct ones, the three counts, and the number of failed items (not counted in the mean). The full rubric and the prompt are in `evals/training/judge.go`.

The judge is an LLM: its scores are not exact, and repeating an eval can differ a little. The reference answer is the dataset's `output`, so what is measured is agreement with it, not truth.

## How the judge works

1. The examples are read from the model's dataset, the first `limit` of them if a limit is set, and go in batches of `batch_size` (default 10, at most 25).
2. The judge gets a batch as a JSON array (`id`, `question`, `reference`, `answer` per item) and a rubric, and replies with a JSON array of `{id, score, reason}`. Wording, order and length do not matter, facts, numbers, names, dates and actions do; extra detail is fine unless it contradicts the reference. The items are given as data, with a rule to ignore any instructions inside them. Texts over 4,000 bytes are cut before they are sent. The reply may be wrapped in a code fence or prose; the JSON array is found in it.
3. Items the judge skipped, or gave a score outside 0 to 5, are sent once more; still without a verdict they are marked `failed` ("judge: no verdict returned for this item", or the judge's error). A question the model failed to answer is marked `failed` and not sent to the judge.
4. A run that only gets failures stops instead of burning GPU time: after 2 batches in a row where the model answered nothing (a dead sidecar, weights gone from the volume), or 3 batches in a row where the judge graded nothing (a bad API key, the API down). The eval is then `failed` with the last error, and the batches before it are kept.
5. After each batch its items and the running totals (answered, judged, failed, correct, partial, incorrect, score sum, the judge's calls, tokens and cost) are handed to the sink, which the server stores, so progress is visible while the eval runs.

The logic is a library with no HTTP, sidecar or database in it (`Run(ctx, cfg, examples, generate, judge, sink)` takes the model as a function and the judge as an LLM); `internal/api/training/evals.go` wires it to the sidecar, to the recording of LLM calls and to the database. Its tests use a fake model and judge, with no network. It is separate from the knowledge-extraction evals, which have their own runner in `evals/knowledge` (see [Evals](/operations/evals)); [evals/README.md](https://github.com/deepblue-phoenix/gligabao/blob/main/evals/README.md) compares the two.

## API

All under `/v1/gb/training/`, with `?db=<name>` to pick the database like the other training endpoints.

| Endpoint | |
|---|---|
| `POST /models/{id}/evals` | Starts an eval. Optional JSON body: `limit` (only the first n questions; default all), `batch_size` (pairs per judge call, 1 to 25, default 10), `judge_model`, `max_tokens` (default 1024), `temperature` (default 0.1). `202` with the eval; `400` bad body or dataset not usable, `404` unknown model, `409` one running, `503` no sidecar or no LLM. |
| `GET /models/{id}/evals[?limit=n]` | `{"evals": [...]}`, newest first (without items). |
| `GET /evals/{id}` | `{"eval": {...}, "items": [...]}` with the items stored so far, in dataset order. |
| `POST /evals/{id}/cancel` | Stops a running eval (`202`); `409` if it is not running. |

An eval has `status`, `dataset`, `dataset_sha256`, `params` (batch size, max tokens, temperature, limit), `judge_model`, `num_examples`, the counters `num_answered`, `num_judged`, `num_failed`, `num_correct`, `num_partial`, `num_incorrect`, `score_sum` (mean = `score_sum / num_judged`), `num_batches`, `judge_calls`, `judge_input_tokens`, `judge_output_tokens`, `judge_cost_usd`, `error`, `created_at` and `finished_at`. An item has `idx`, `batch`, `instruction`, `input`, `reference` (the dataset's answer), `response` (the model's), `status` (`judged` or `failed`), `error`, `score`, `reason`, `input_tokens`, `output_tokens` and `duration_ms`.

## Tables

`gb_trained_model_evals` (one row per eval) and `gb_trained_model_eval_items` (one per question, cascading), in SQLite and PostgreSQL; the columns are documented in `internal/db/relational/sqlite/db_schema.go`. Go: `relational.RecordTrainedModelEval`, `SaveTrainedModelEvalBatch`, `FinishTrainedModelEval`, `GetTrainedModelEval`, `ListTrainedModelEvals`, `ListTrainedModelEvalItems`.
