Link prediction with the GCNII* model

A new node arrives in a cluster (a graph). How likely is it to be connected to each node that is already there? This page explains, in one place, how gligabao answers that with the per-user GCNII* model running in sargo.

TL;DR

  • Link prediction is a pipeline of the per-user GCNII* model, next to infer (class of a graph) and embed (embedding of a graph).
  • The model turns a graph into one embedding per node. A pair of nodes is scored from their embeddings in one of two ways: cosine (free, no extra training) or head (a small trained link head).
  • A user's model can hold both: it keeps classifying and gets a link head. A user without a trained model gets 404.
  • Use the order of the scores, not their absolute values.

1. The problem

Given a graph and a new node with a type and maybe some links it is already known to have, give each existing node a score for "the new node is connected to it". This is link prediction at the node level.

The model of a user is a GCNII* graph classifier. Its layers turn the graph into one embedding per node (the output of the last layer, hidden floats per node). The classifier averages them into one graph embedding and applies a classification head. Link prediction reuses the node embeddings, before that averaging.

MethodScore of a pair (u, v)NeedsWhere the knowledge comes from
cosinecos(hu, hv), in [0, 1] (the embeddings are ReLU outputs)only a trained classification model (no extra training)nowhere extra: whatever the classification training made the embeddings mean. A heuristic: nodes the classifier embeds alike score high.
headsigmoid(w · (ĥu ⊙ ĥv) + b), a probabilitya link training (section 6)a training whose only goal is to predict edges, on held-out edges, so its score is something the model was asked to be right about.

2. End-to-end data flow

A request enters gligabao, is checked by the Go client, goes to sargo, which loads the user's weights, grows the graph with the new node, runs the model and ranks the scores.

3. The route

POST /v1/gb/training/gcnii/link, acting as the user of the request (the gb-user-id header or the API key; never a body field). It needs training mode and sargo, like the other GCNII* routes.

  "graph": {"n": 4, "edges": [[0,1],[1,2],[2,3]], "nodes": [{"name": "a", "type": "person"}, ...]},
  "node":  {"name": "new", "type": "person", "neighbors": [1]},
  "top_k": 3

FieldMeaning
graphThe cluster: the same graph document as infer and embed (n, undirected edges, optional nodes with name and type).

Answer:

{"method": "head", "node": 4, "nodes": 4, "scores": [{"node": 2, "name": "c", "score": 0.93, "connected": false}, ...]}
  • method is the one that scored; node is the index the new node gets in the augmented graph (= nodes).
  • scores has one item per node of the graph (or top_k), best first (ties by node index).
  • name is only there when the node has one; connected is true for the nodes given in neighbors (those links are known, not predicted).

Errors: 400 (no user, a bad graph or node, a neighbor outside 0..n-1, top_k < 1), 404 the user has no trained model, 503 sargo has no per-user models, 502 sargo did not answer.

4. How a score is made

  1. The new node is appended to the graph as node n, with its type and an edge to each of neighbors.
  2. The trained model runs its layers on this augmented graph and gives one embedding per node: the output of the last GCNII* layer (hidden floats), the vector that is averaged into the graph embedding of embed, before the classification head.
  3. cosine: the score of the pair (new node, node i) is the cosine similarity of their node embeddings. Layer outputs are ReLU outputs, so the score is in [0, 1] (0 also when one vector is all zeros).
    head: the score is sigmoid(w · (ĥu ⊙ ĥv) + b) on the unit-length embeddings, with w and b the hidden + 1 weights of the link head: a probability of the link.

5. The link head

ĥ is h scaled to unit length (a zero embedding stays zero). The head has hidden + 1 parameters: a weight wf per embedding feature and a bias b (GcniiStar::link, a Vec<f32> of hidden weights followed by the bias).

logit(u, v) = b + Σ_f  w_f · ĥ_u[f] · ĥ_v[f]
score(u, v) = sigmoid(logit(u, v))
  • Symmetric: score(u, v) = score(v, u), the links are undirected.
  • Unit-length embeddings: the features of the embeddings of a deep GCNII* are small and vary in scale between graphs; normalizing makes the head's input comparable and the training stable. With wf = 1 and b = 0 the logit is exactly the cosine.
  • Initial state: a new head starts as a scaled cosine scorer: every wf is 6 plus a little noise (std 0.1) and b = -3 (LINK_INIT_SCALE in model.rs). At step 0 the head ranks nodes like the cosine method (and spreads the probabilities over the sigmoid's useful range); training has to improve on that, and a head that does not learn is as good as the cosine, not worse.
  • A diagonal bilinear form on purpose: few parameters, symmetric by construction, cheap exact gradients. It can re-weight embedding features (which ones matter for "these two are linked") but cannot model interactions between different features.

6. Training the head

The head is trained on the same kind of data as the classification (graphs {n, edges, nodes?}), next to it. A new head starts as a scaled cosine scorer, so it starts where the cosine method is and has to improve on it. One training example is one graph, rebuilt every epoch (make_example in link_train.rs).

The steps of one example

  1. Split the edges. A holdout fraction (default 0.2, rounded, at least 1 and at least 1 left) of the edges, picked at random, are taken out. They are the positive pairs.
  2. Hide them. The adjacency of the graph is rebuilt without those edges.
  3. Negative pairs. As many random node pairs that are not edges of the full graph (neither kept nor held-out) as there are positives, distinct, a < b. For a nearly complete graph there may be fewer; a graph with no non-edge, with fewer than 2 edges or fewer than 3 nodes is skipped for that epoch.
  4. Forward. The encoder runs on the hidden-edge graph; the head scores every pair from the node embeddings.
  5. Loss. The mean binary cross-entropy (with logits) of the pairs; the "pair acc" of the log is the share of pairs on the right side of 0.5.
  6. Backward. The gradient of the head is exact. The gradient on the embeddings goes back through the unit-length normalization (dh = (dĥ − ĥ (ĥ·dĥ)) / |h|) and, if the encoder is trained, through the GCNII* layers (backward_encoder in model.rs, the same code as the classification backward after its pooling step). The finite-difference test of link_train.rs checks the head and every encoder tensor.
  7. Step. Plain SGD with learning rate lr, one step per batch graphs (the gradients of the batch are summed, each already divided by the batch size).

The randomness is per graph and epoch (seed, the epoch and the graph's index), so an example does not depend on the order the graphs are visited in; the same seed repeats the training.

7. What is trained: encoder and init

encoderTrainedThe classification part
frozenonly the head (hidden + 1 numbers)untouched, bit for bit; needs a model to start from (init)
trainthe head and the whole encoder, by the link losswith class_weight = 0 left as it was; with class_weight > 0 the classification loss of each graph (cross-entropy of its label, on the full graph) times class_weight is added to the encoder's gradient, so both heads train at once
  • frozen adds link prediction to a model people already use, without changing a single class probability.
  • train lets the encoder organize the embeddings for links. Alone (class_weight 0) the classification head becomes stale and meaningless; the model is a link model. With class_weight > 0 it is a multi-task model: how well each task does depends on the weight and has to be measured (see section 8).
  • Not allowed (an error, 400 over HTTP): frozen without init; class_weight > 0 with frozen; class_weight > 0 with a graph whose label is outside the classes of the starting model.

Where it starts: init

  • init true: start from the user's current model (its encoder, its classification head and its classes; a head it already has is trained on). The default when the encoder is frozen. A user without a model gets 404.
  • init false: a new model: hidden/depth (default 16/16) and the node-type vocabulary from the training graphs, a new classification head with one output per class found, a new link head. Needs encoder train. This is the default for train; set "init": true to fine-tune the current model.

Data

The same graph documents as the classification: {n, edges, nodes?: [{name?, type?}]}. A class is not needed for a link training unless class_weight > 0 (sargo fills in a placeholder class _ otherwise; the model's classes are then those of the starting model, or ["_"]). Through the jobs API a dataset is built as for the classification (graphs and LLM classes, at least 2 classes), so a dataset training still needs the classes; graphs sent in the body do not. Only graphs with at least 2 edges (and 3 nodes) give link examples; small graphs are skipped; a dataset with none is an error.

The mean link loss of each epoch is reported like the classification loss (epoch_losses, epoch_loss). The job reports link_loss, and when done link_eval (and val_link_eval if it had validation graphs): the test below on the training and validation graphs, for both methods. They are also in the run meta (GET /v1/gb/training/jobs/{id}/meta) and the params of the model row. A later classification training replaces the model and so drops its link head.

8. Testing both methods

POST /v1/gb/training/gcnii/link/eval with {"graphs": [{n, edges, nodes?}, ...], "nodes"?, "reveal"?, "seed"?} tests both methods with the user's model on the same cases. The test (link_eval.rs) imitates how the route is used: a node arrives, some links are known, find the others.

  1. Hold out nodes. From each graph, up to nodes (default 5) nodes with at least 2 neighbours (graphs of at least 4 nodes) are picked at random (seed, default 1; the same seed gives the same cases).
  2. Split its neighbours. The node is removed with its edges (the other nodes are renumbered). A reveal fraction of its neighbours (default 0.5, rounded, at least 1 and at least 1 left) are given as the neighbors of the new node; the rest are the targets.
  3. Score. The node is added back as a new node (its type, the known neighbours) and the method scores it against every node of the graph.
  4. Rank. The candidates are all nodes except the known neighbours; the targets are the positives, the other candidates the negatives.

Answer:

{"cases": 200, "cosine": {"cases": 200, "auc": 0.87, "mrr": 0.61, "hits_at_10": 0.98}, "head": {"cases": 200, "auc": 0.88, "mrr": 0.62, "hits_at_10": 0.99}}
MetricMeaning
aucthe probability that a random target scores above a random non-neighbour (ties count 0.5). 0.5 is random, 1 is perfect
mrrthe mean of 1 / rank of the best-ranked target; ties are ranked against the target (pessimistic)
hits_at_10the fraction of cases with a target among the 10 best candidates

Metrics are averaged over the cases (a case without a positive or a negative candidate is skipped). Both methods are scored on exactly the same cases, so the numbers are comparable (cases is the same). head is null for a model without a link head. A graph set where no node qualifies is an error.

Remember
  • The test is in-sample for the graphs a model was trained on (the training saw the edges of those graphs, in a different split). A link job reports link_eval on its training graphs and, if it had validation graphs, val_link_eval: use validation graphs (graphs the training never saw) to compare fairly. Test on graphs the model was not trained on, or the numbers are in-sample.
  • With few cases the numbers are noisy: raise nodes or give more graphs, and compare on the same seed.
  • Training is on held-out edges, the test is on held-out nodes. The difference is on purpose: it measures what the pipeline is used for.

9. The weights file

A model with a link head is a GCNL file: the same layout as the deepblue-compatible GCN* file (header, type vocabulary, all the parameters of the model) with the hidden + 1 floats of the head appended, and GCNL as the magic. A model without a head is still the exact GCN* file. weights::load reads both; the head is None for a GCN* file. So:

  • the classification training writes GCN* (and so drops a link head: it makes a new model);
  • a link training writes GCNL to the same place (<models_dir>/<hex user>/model.weights), and the weights store and the cluster sync (see the GCNII* guide) copy it as any other file; a GCNL file is not loadable by the deepblue engine.

10. How to use it

Over HTTP (gligabao)

  1. Train the classification as usual (POST /v1/gb/training/jobs, "model_type": "gcnii").
  2. Train the head: the same endpoint with "task": "link", e.g. {"model_type": "gcnii", "task": "link", "graphs": [...], "validation": [...], "epochs": 40, "lr": 0.05} (frozen, from the user's model) or with "encoder": "train", "class_weight": 1 (both heads; init is false so a new model; set "init": true to fine-tune the current one). The job record has task, and when it is done link_loss, link_eval and val_link_eval. A running link job shows up in GET /v1/gb/training/jobs?model_type=gcnii as any job.
  3. Test: POST /v1/gb/training/gcnii/link/eval with graphs the model has not seen.
  4. Use: POST /v1/gb/training/gcnii/link (method head; the default once the model has a head, cosine to compare).

On the command line (no server)

# 1. a classifier (as before)
sargo gcnii train DS --save cls.w --epochs 15 --hidden 16 --depth 4
# 2. the cosine method, measured on the classifier alone
sargo gcnii eval-link DS --load cls.w
# 3. a frozen head on top of it (the model keeps classifying)
sargo gcnii train-link DS --save frozen.w --init cls.w --epochs 40 --lr 0.05
# 4. both heads at once, from scratch
sargo gcnii train-link DS --save joint.w --encoder train --class-weight 1 --epochs 40 --lr 0.02 --hidden 16 --depth 4
# 5. compare: every eval prints both methods on the same cases
sargo gcnii eval-link DS --load frozen.w
sargo gcnii eval-link DS --load joint.w
sargo gcnii eval DS --load joint.w          # and what the classification kept
# 6. predict
sargo gcnii link cluster.json --load frozen.w --type person --neighbors 1,4 --top-k 5 --method head

11. Choosing, and reading the results

  • Start with cosine (free) and measure it. Train a frozen head and measure again: if head is not clearly better on validation graphs, keep the cosine.
  • frozen when the classification must not change; train with class_weight when both tasks matter and you can afford to check that the classification did not get worse (eval on the classification, and the class metrics of the job); train with 0 for a model only meant for links.
  • The head pays off when the structure says more about links than "looks alike": when types or the embeddings already separate the communities (a toy graph made of typed clusters) both methods are about equal. In a first run on synthetic community graphs, AUC was 0.872 for the cosine, 0.873 for the frozen head and 0.881 for both heads trained from scratch; expect differences to show on harder, real data.
  • A new node without known neighbours is scored from its type alone, whichever method: give it the links you know.
  • The score of the head is a probability in the sense of the training distribution (balanced positives and negatives); it is not calibrated to how rare real links are, so use it to rank, and pick a threshold on data you have.
  • The model is deep and smooths embeddings; very different graph sizes between training and use change the picture. Test on data like the use.

12. Limits

  • The cosine method uses a model trained to classify graphs, not to predict links. A high score means "this node looks like that one, in the context of this graph" (same kind of type and neighborhood); it is a ranking, not a calibrated probability of an edge.
  • A new node without neighbors has only its type (and degree 0) as features, so it mostly ranks the nodes of the same type first. Give it the links it is already known to have for a better signal.
  • The model has many layers, which smooths the embeddings: scores of a cluster can be close together; use the order, not the absolute values.
  • The head is trained on held-out edges, not on held-out nodes: a new node differs a bit from that (it has only the links you know), so test with the node-level test of section 8. On graphs where the node types already tell the communities (the usual case in a toy), both methods can be about equal; the head pays off when the structure says more than the cosine can.

13. Other entry points

  • sargo: POST /v1/gcnii/link and POST /v1/gcnii/link/eval take the same bodies plus an optional user_id (without it the global [gcnii] weights model is used). POST /v1/gcnii/train takes "task": "link" with holdout, encoder, class_weight, init; without a class on the graphs unless class_weight > 0.
  • Command line (sargo gcnii ..., JSON on stdout):
    • link GRAPH.json|- --load w.bin [--type T] [--name N] [--neighbors 0,3] [--top-k K] [--method cosine|head]
    • train-link DIR --save out.w [--init cls.w] [--encoder frozen|train] [--class-weight X] [--holdout X] [--epochs N] [--lr X] [--batch N] [--seed N] [--hidden N] [--depth N]
    • eval-link DIR --load w.bin [--nodes N] [--reveal X] [--seed N]
    To compare the approaches: train a classifier, eval-link it (the cosine numbers), train-link --init it (frozen head) and train-link --encoder train [--class-weight 1] (from scratch), then eval-link each.
  • Weights file: GCNL for a model with a link head, GCN* otherwise (section 9).
  • Go client: sargo.Client.GCNIILink, GCNIILinkEval and the Task/Holdout/Encoder/ClassWeight/Init fields of GCNIITrainRequest (internal/sargo/gcnii.go) check the input before sending. The handlers are model.Link and model.LinkEval (internal/api/model); the training goes through internal/training/gcnii like the classification.
