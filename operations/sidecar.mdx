`side_car/`, `side_car/ai_train/`, `Dockerfile.sidecar`, `docker-compose.yml`, `run_build_sidecar.sh`, `internal/sidecar/sidecar.go`, `internal/sidecar/training_jobs.go`, `internal/sidecar/training_datasets.go`

The sidecar is a small Python service that runs next to the Go server and that the server talks to over HTTP. It exists for work that is easier to do in Python (libraries that have no good Go equivalent). **Today the service itself is only a skeleton**: it starts, listens, and answers a health check. Alongside it sits a separate, much larger part: Gemma-4 fine-tuning and inference on remote (cloud GPU) infrastructure, with its own web API; see [Remote training](#remote-training). The Go server calls that web API through the Go client to start training jobs (the admin endpoint `POST /v1/gb/admin/api/training/jobs`) and records each one; this is documented in the [Training](/training/overview) section.

## The service

`side_car/main_sidecar.py` is a [FastAPI](https://fastapi.tiangolo.com/) app run by [uvicorn](https://www.uvicorn.org/). Dependencies are in `side_car/requirements.txt`.

| Endpoint | Response |
|---|---|
| `GET /health` | `200 {"status": "ok"}` |

Configuration is by environment variable:

| Variable | Default | Meaning |
|---|---|---|
| `SIDECAR_HOST` | `127.0.0.1` | Interface to listen on. Local only by default, as the sidecar has no authentication. |
| `SIDECAR_PORT` | `8787` | Port to listen on. |

Run it without a container:

```sh
cd side_car
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python main_sidecar.py              # listens on 127.0.0.1:8787
curl http://127.0.0.1:8787/health
```

It is separate from the FastAPI service above, is not imported by `main_sidecar.py`, and is not copied into `Dockerfile.sidecar`. It has its own section of this site, [Training](/training/overview):

## The container

`Dockerfile.sidecar` (in the repo root; the plain `Dockerfile` is the Go server's) packages the sidecar on `python:3.13-slim`: it installs the requirements, copies `main_sidecar.py`, runs as the non-root user `sidecar` and starts `python main_sidecar.py`. The image sets `SIDECAR_HOST=0.0.0.0` (a container must listen on all interfaces for a published port to reach it) and exposes `8787`.

```sh
./run_build_sidecar.sh                         # builds gligabao-sidecar:latest
./run_build_sidecar.sh myrepo/sidecar:dev      # or a name of your choice
docker run --rm -p 127.0.0.1:8787:8787 gligabao-sidecar:latest
```

Publish the port on `127.0.0.1` (as above) unless the sidecar must be reachable from other machines: it has no authentication.

### With docker compose

`docker-compose.yml` (in the repo root) starts the server and the sidecar on the same network (`gligabao`):

```sh
export ANTHROPIC_API_KEY=...
docker compose up --build
```

On that network the server reaches the sidecar at `http://sidecar:8787` (the service name; `127.0.0.1` would be the server's own container). The server starts only once the sidecar's `/health` check passes. Both ports are published on `127.0.0.1` only; the server's data lives in the `gligabao-data` volume.

## The Go client

`internal/sidecar` is the only package in the Go code that knows the sidecar's HTTP API: `sidecar.go` has the client and `Health`, `training_datasets.go` and `training_jobs.go` the training calls.

```go
c := sidecar.New("")                       // "" is sidecar.DefaultBaseURL, http://127.0.0.1:8787
resp, err := c.Health(ctx)                 // resp.Status == "ok"
```

- `sidecar.New(baseURL)` returns a `*Client` with a 30 second timeout per request. A trailing `/` on the URL is ignored.
- `Client.Health(ctx)` calls `GET /health`. It returns an error if the sidecar cannot be reached, answers with a status other than 200, sends a body that is not the expected JSON, or reports a `status` other than `"ok"`.
- `Client.StartTrainingJob(ctx, req)` calls `POST /training/job_start` and returns the `TrainingJob` the sidecar reports; `Client.UploadTrainingDataset(ctx, filename, content)` and `Client.ListTrainingDatasets(ctx)` call `POST /datasets/upload` and `GET /datasets/list`. See [Training jobs](/training/jobs#the-go-client) and [Training datasets](/training/datasets#go-client).
- Errors name the method and path (`sidecar GET /health: ...`) and, for a bad status, include the start of the response body.

The tests (`internal/sidecar/sidecar_test.go`) run the client against an `httptest` server, so they need neither Python nor Docker.

## Adding an endpoint

1. Add the route to `side_car/main_sidecar.py` (and any new package to `side_car/requirements.txt`).
2. Add a method to `Client` in `internal/sidecar` (a new file per topic, like `training_jobs.go`), with typed request and response structs. Keep all calls to the sidecar in that package.
3. If the Go server should start it, add an admin handler in `internal/api/admin` that takes the client through a small interface, as `StartTrainingJobOf` does.
4. If the Dockerfile must copy new files, update `Dockerfile.sidecar` (it copies `main_sidecar.py` only).
5. Document the endpoint in the table above.
